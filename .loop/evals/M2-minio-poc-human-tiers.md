eval: M2-minio-poc-human-tiers

Definition of Done: with F2 applied and the MinIO job redeployed, a human authenticates to the MinIO console at exactly one of three tiers (Admin / Reader / Writer), gets the S3 access that tier's policy grants, and cannot cross into a tier whose Vault assignment excludes them.

| Behavior | Input | Expected | Scorer | Threshold |
|----------|-------|----------|--------|-----------|
| MinIO exposes three tiered OIDC role providers | `mc admin config get minio identity_openid:admin` (repeat for `:writer`, `:reader`) against the redeployed job | All three named configs present; each block's `role_policy` equals its tier policy name (`minio-admin`/`minio-writer`/`minio-reader`) with non-empty `config_url`, `client_id`, and `redirect_uri` | deterministic check (`mc admin config get`) | 100% |
| The three tier policies grant their intended action sets | `mc admin policy info minio minio-admin` (repeat for `minio-writer`, `minio-reader`) | `minio-admin` = full access; `minio-writer` = put/get/list (plus accepted multipart actions); `minio-reader` = get/list and no `s3:PutObject`; no "policy does not exist" and zero exit | deterministic check (`mc admin policy info`) | 100% |
| Each Vault OIDC client is bound to exactly its own tier's assignment (F2) | `vault read identity/oidc/client/<tier>` and `vault read identity/oidc/assignment/<tier-assignment>` per tier | Each client returns `client_id`, `redirect_uris` matching the console redirect, and an `assignments` entry for its tier; each assignment lists only that tier's group (`minio-admins`/`minio-writers`/`minio-readers`) in `group_ids`/`entity_ids`, never another tier's | deterministic check (`vault read identity/oidc/client` + assignment) | 100% |
| A reader authenticates to the Reader tier and gets read-only S3 | A scripted `minio-readers`-only entity obtains an id_token via the reader OIDC client and exercises the reader console session | Session assumes `minio-reader`; list/get succeed, put/upload denied; access is read-only and confined to the reader tier | model + rubric (adversarial review agent) | 4/5 |
| A reader is refused the Admin client (guardrail: cross-tier deny) | The same `minio-readers`-only entity calls `vault read identity/oidc/provider/<provider>/authorize client_id=<admin-client-id> ...` | Refused: no authorization `code`; endpoint returns `access_denied` because the reader entity is not in the admin client's assignment | deterministic check (`vault read .../authorize` returns `access_denied`) | 100% |
| Manual browser close-out confirms the three-button console and tier gating (human-scored) | In a browser on the MinIO console (port 9001): a `minio-readers` member clicks Reader then Admin; a `minio-admins` member clicks Admin | Three login buttons render; reader is read-only and refused at the Vault consent/authorize step for Admin; admin member has full access; result recorded in acceptance notes | human + rubric (manual close-out) | 4/5 |
